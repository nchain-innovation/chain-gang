* v0.11.2 - Two robustness fixes. Additive API only, so cargo treats this as a compatible upgrade: `util::read_exact_vec`, `util::bounded_capacity`, `util::MAX_PREALLOC_ELEMENTS` and `script::stack::pop_bigint_checked_minimal` are new, and nothing existing changes shape. Wire-format reads no longer size an allocation from a sender-controlled length prefix: 17 sites across `tx_in`/`tx_out`, `tx`, `block`, `merkle_block`, `filter_add`/`filter_load`, `protoconf`/`createstrm`, `version` and `reject` now grow a buffer as bytes arrive via `util::read_exact_vec`, or cap a speculative reserve with `util::bounded_capacity`, so a 27-byte transaction declaring a 2^48-byte script is an error rather than an allocation-failure `SIGABRT` that a consumer cannot catch. Script evaluation applies minimal *number* encoding only where a stack item is decoded as a number, not to every push: a 33-byte public key or a 20-byte hash ending `0x00` or `0x80` is ordinary data, and rejecting it as `Non-minimal push data` refused roughly 1 in 128 standard P2PKH spends. Minimal-*push* (BIP-62) is unchanged, and minimal-number enforcement now also covers the bigint arithmetic operands it previously missed
* v0.11.3 - WhatsOnChain endpoint fixes. No API change: `Balance` and `UtxoEntry` keep their fields, and the new types are internal. `get_utxo` reads `/address/{addr}/unspent/all` and follows every page, where it previously read the undocumented `/unspent` and stopped at 1000 entries with no way to ask for the rest, so a busy address came back silently truncated and a caller could not tell 1000 UTXOs from 50,000; on `1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa` that is 20960 entries rather than 1000, the old result being a strict subset of the new one. Unconfirmed outputs are now recognised by the entry's `status` field, falling back to `height == 0` as before. `get_balance` reads `/confirmed/balance` and `/unconfirmed/balance`, the endpoints that replaced the undocumented combined `/balance`, reproducing its figures to the satoshi. Both endpoints report failures in the body with HTTP 200, so an error is no longer read as an empty UTXO set or a zero balance. **Paging and the split balance turn one request into several, and WhatsOnChain rate limits**, so requests now back off on 429/502/503/504, matching what the Python client already did; `tokio` joins the `interface` feature for its timer, having already been present through `reqwest`. The parallel Python client is changed to match. CI actions moved off the deprecated Node 20 runtime
* v0.11.4 - Fixes `get_utxo` failing with ``missing field `height` `` whenever an address had an unconfirmed output. WhatsOnChain omits `height` entirely on a mempool entry rather than sending 0, and v0.11.3 required the field, so one payment sitting in the mempool failed the whole page and the address could not be read until it confirmed. An absent height now means unconfirmed, alongside the `status` field and the `height == 0` of older responses; the Python client agrees on all three. Additive API only, so cargo treats this as a compatible upgrade: `UtxoEntry` is untouched and the type the fix changed is internal. The test fixtures that hid this, which wrote `"height": 0` for unconfirmed entries, now carry a real mempool entry instead. `WocInterface::set_max_requests_per_second`, with a `with_max_requests_per_second` builder form, is new and off by default; it bounds the HTTP requests the interface issues rather than the calls made to it. That distinction only started to matter in v0.11.3: `get_balance` became two requests and `get_utxo` one per 1000 UTXOs, so a consumer pacing its own calls at 3/s could issue 21 requests inside one 333ms slot, and could not fix it from outside because every request went through a bare `reqwest::get` or a locally built `Client` with no hook to supply. Every request in the interface now goes through one paced funnel, including the broadcast POST and the per-page retries. Everything else since v0.11.3 is CI and tooling and does not reach the published artifact: runners pinned off `ubuntu-latest` and then moved deliberately to 26.04 (CS-442, CS-444, CS-459), the Rust cache key scoped to the runner image after a stale cross-image cache produced a linker error that looked like an image incompatibility and was not, and an opt-in pre-commit hook rejecting workflow YAML that GitHub Actions would refuse to load
* v0.11.5 - WhatsOnChain's `/unspent/all` keeps listing a confirmed output after a mempool transaction spends it, flagging it only as `isSpentInMempoolTx`; `get_utxo` ignored that and returned those outputs as spendable, so a caller building on one made a transaction the network could only treat as a double spend. Both the Rust and Python clients now leave them out, which makes the WhatsOnChain interface agree with a node's own `listunspent` about what can still be spent. **Behaviour change, but a fix**: `get_utxo` returns fewer entries while a mempool spend is pending
* v0.11.6 - **Security fix: `Tx::validate` accepted spends without a signature.** An unlocking script made of a single push opcode with no data after it, `0x1a` for a P2PKH output, passed for any output whatever its locking script, in every era setting, through `Tx::validate`, `Tx::validate_at_height` and Python's `Tx.validate`. Two faults combined. `is_push_only` stepped over a push whose data ran past the end of the script and called it push-only, where the node's `IsPushOnly` is false and evaluating it is `BAD_OPCODE`. And version-1 inputs were evaluated as one script, `unlock OP_CODESEPARATOR lock`, so that push took the separator and the whole locking script as its data and left a true value. The node rejects such a spend, so a transaction chain-gang called valid could be one the network never accepts: anything that checks incoming payments with `Tx::validate` should upgrade. `is_push_only` now rejects truncated pushes, and version-1 inputs are evaluated as the node's `VerifyScript` evaluates them, the unlocking script on its own and then the locking script on the stack it leaves (`eval_unlock_then_lock`, newly public). Version-2 inputs under Chronicle were already evaluated in two phases and were not affected. Also in this release: a pushed byte equal to `0xab` or `0xac` could be read as a separator or a checksig when building a P2PKH script code, cutting it mid-hash for roughly 1 in 345 keys, so those signatures failed on chain (CS-483); and the crate is `cargo fmt`-clean, with a CI check to keep it so. Additive API only, so cargo treats this as a compatible upgrade
* v0.12.0 - Consensus fixes to signing and script validation, found by checking chain-gang against bitcoin-sv's own test vectors and a live node instead of against expectations written from a reading of the rules, which is how code and test had been wrong together (CS-491). **Every signature digest that changes is one the node rejected**: signatures that failed on chain with NULLFAIL now verify, and no signature the node accepted is computed differently. `SIGHASH_SINGLE` on the original digest algorithm, which Chronicle signatures and pre-fork ones use, blanked the signed output and signed the free ones (#192). BIP-143 deleted every `OP_CODESEPARATOR` from the script code, where the node keeps the ones after the separator that executed, which also settles CS-488 (#193). The script code started at 0 whenever a script held a single separator, so the opcodes before it were signed too (CS-492). A pushed byte equal to `0xab` or `0xac` could be read as a separator or a checksig, cutting P2PKH script codes mid-hash for roughly 1 in 345 keys (CS-483). **`Tx::validate` now agrees with the node far more closely, in both directions.** It accepts spends it wrongly refused: verification hashed the interpreter's script code a second time, which made `OP_CHECKMULTISIG` and `OP_CHECKSIGVERIFY` scripts holding a separator fail; an empty signature aborted the script instead of failing the check (#210); `BIN2NUM` checked its input against the number limit rather than its result, rejecting padded inputs (#36); push-only unlocking scripts were required before Genesis, where the node only requires them for P2SH (#199); and valid pre-Genesis P2SH spends failed on the clean-stack rule because their redeem script never ran. It rejects spends it wrongly accepted: the redeem script of a pre-Genesis P2SH output is now run, so a spend whose redeem script fails is rejected (#201); signatures with an undefined sighash type are rejected where FORKID is required (#208); transactions creating a P2SH output after Genesis are rejected, the check having never fired (#202); and spends earlier versions signed and then accepted under the same wrong rule, for example `SIGHASH_SINGLE` on the original algorithm. **Consensus and policy are now separate (#205).** `Tx::validate` still checks what the node's mempool checks, including the node's policy rules for non-malleable transactions: minimal pushes and numbers, now matching the node's single-byte rule (#203), an empty multisig dummy, and a clean stack. The new `Tx::validate_consensus` and `Tx::validate_at_height_consensus`, and the `CONSENSUS_ONLY` script flag, check consensus only, and `Block::validate` uses them: it used to reject valid blocks, including one a live node accepted. The minimal-`IF` rule is gone everywhere, the node never applying it. **A minor version, so dependents must opt in**: the API only gains additions (`sighash_from_script_code`, which a `Checker` implementation should use, `CONSENSUS_ONLY`, `Tx::validate_consensus` and `Tx::validate_at_height_consensus`) and nothing existing changes shape, but validation behaviour moves enough that it is not shipped as a patch, and cargo treats 0.12 as incompatible with 0.11, so a requirement of `"0.11"` must be raised to `"0.12"` to pick it up. `Script::append_num(-1)` and Python's `insert_num(-1)` emit `01 81` rather than `OP_1NEGATE`, a push the node's policy rejects. The Python `tx-engine` package calls the same Rust code and gets every fix. Its `Wallet.to_int` and `Wallet.from_int` now convert through bytes instead of evaluating a constructed `int('...')` expression; `from_int` rejects negative integers, which it used to negate silently, and `from_int`, `from_hexstr` and `from_bytes` raise `ValueError` for a key outside the secp256k1 range instead of panicking, which Python saw as a `PanicException` that `except Exception` does not catch (#34). The other inputs that panicked the same way now raise `ValueError` too: an out-of-range input index to the `sig_hash` functions, a `TxIn` whose `prev_tx` is not a 32-byte hex txid, malformed tokens in `Script.parse_string`, and an address that decodes to an empty payload (#216). `Script.parse_string` and `append_integer` now encode numbers outside the 32-bit range instead of panicking; past 64 bits `parse_string` used to read them as strings. Numbers longer than 75 bytes are pushed with `OP_PUSHDATA1` or `OP_PUSHDATA2`, where a raw length byte used to be written that the interpreter reads as an opcode. In Rust, printing a `tx` or `block` `Reject` whose data is shorter than a hash no longer panics, which a peer could trigger through debug logging, and `TestInterface` returns an error from the methods it does not support instead of panicking. The vectors are bitcoin-sv's, under the Open BSV License rather than MIT, so `tests/data/` is excluded from the published crate; its tests skip when it is absent if `CHAIN_GANG_VECTORS_OPTIONAL=1` is set. The crate is also `cargo fmt`-clean now, with a CI check to keep it so, and CI's Python tests install the wheel they build by its path, so they always test the branch rather than a published release of the same version
